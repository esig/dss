== Attestations

An attestation is a digitally signed document that contains claims about a subject (for example, a person, organization or device).

Examples include:

* a person identity data (PID);
* a driving licence;
* a diploma;
* a professional qualification;
* an authorization or role;
* and others.

An attestation may allow the holder to reveal only the claims required for a particular interaction.

Notable examples of those attestation formats utilization in the context of eIDAS (cf. <<R12>>) are Electronic Attestations of Attributes (EAA) and Person Identification Data (PID).

Electronic Attestations of Attributes are digital identity credentials defined within the European Digital Identity (EUDI) framework. They allow the selective disclosure of identity attributes (claims) to a verifier, without exposing the full content of the credential.

From the perspective of the DSS, both are handled identically - the only difference is the set of claims contained in the attestation.

=== Workflow and implementation

DSS supports the complete lifecycle of attestations:

1. The issuer creates the attestation payload.
2. The issuer signs the attestation.
3. The issuer transfers the attestation to the wallet with (optional) selectively disclosable claims.
4. The wallet selects information to be presented to a relying party.
5. The wallet creates a key binding signature.
6. The wallet issues an attestation presentation to a relying party (Verifier).
7. The verifier validates authenticity of the attestation presentation.

.The attestation lifecycle
----
        +-------------------+
        |     Issuer        |
        +-------------------+
                │
                │ 1. Create attestation payload
                ▼
         Attestation Payload
                │
                │ 2. Sign attestation payload
                ▼
         Signed Attestation
                │
                │ 3. (Optional) Attach
                │    selective disclosures
                ▼
         Issued Attestation
                │
                │ Transfer to holder
                ▼
        +-------------------+
        |     Wallet        |
        +-------------------+
                │
                │ 4. (Optional) Select claims
                │    to be disclosed
                ▼
         Selective Disclosures
                │
                │ 5. (Optional) Key binding
                ▼
         Key Binding signature
                │
                │ 6. Issue presentation
                ▼
         Attestation
         Presentation
                │
                │ Presented to relying party
                ▼
        +-------------------+
        |     Verifier      |
        +-------------------+
                │
                │ 7. Validate
                ▼
         Validation report
----

Three parties typically participate in the lifecycle.

Issuer:: Creates and signs attestations.
Wallet:: Stores the issued attestation and creates attestation presentations.
Verifier:: Receives and validates attestation presentations.

The same workflow applies to both supported attestation formats:

* **SD-JWT** (Selective Disclosure for JSON Web Tokens) (<<R35>>) and **SD-JWT VC** (Selective Disclosure JWT Verifiable Credential) (<<R36>>);
* **ISO/IEC 18013-5 mdoc** (Mobile Document) (<<R38>>).

=== Creation

The attestation API separates the lifecycle into three logical workflows.

[cols="1,1,4"]
.Attestation creation services
|===
|Interface |Actor |Purpose

|`AttestationService`                |Issuer   |Creates the payload, prepares the Data To Be Signed (DTBS), and embeds the issuer signature.
|`AttestationSDService`              |Issuer   |Extends attestation creation with support for selective disclosures.
|`AttestationPresentationService`    |Wallet   |Creates holder presentations from issued attestations.
|===

Concrete implementations, such as `SDJWTService` and `MdocService`, implement all three interfaces, allowing a single service instance to be used throughout the complete lifecycle.

==== AttestationService

`AttestationService` provides utilities for an attestation payload creation, based on the parameters, as well as signing of the attestation.

The signed attestation is the credential that represents an issuer's signature authenticating the attestation's payload.

At this stage it contains the issuer signature but has not yet been packaged with the disclosures that will be delivered to the holder. See <<AttestationSDService>> for packaging an attestation with selectively disclosable claims.

The service is typically used by an attestation issuer.

The following methods are provided within the service:

* `#getDataToSign(DSSDocument, SerializableSignatureParameters)` - creates the format-specific data to be signed (DTBS) from an existing attestation payload.
* `#getDataToSign(AttestationPayloadParameters, SerializableSignatureParameters)` - creates the format-specific data to be signed (DTBS) using the payload parameters configuration. The method generates the attestation payload from the supplied parameters before computing the data to be signed.
* `#signAttestation(DSSDocument, SerializableSignatureParameters, SignatureValue)` - produces a signed attestation by embedding the provided signature value into an existing payload.
* `#signAttestation(AttestationPayloadParameters, SerializableSignatureParameters, SignatureValue)` - generates an attestation payload from the supplied parameters and embeds the provided signature value into the resulting attestation.

WARNING: All input parameters shall be equivalent on both `getDataToSign` and `signAttestation` method calls. This especially concerns `SerializableSignatureParameters` and `AttestationPayloadParameters`, including the same `Date` definition for mandatory parameters (such as signing time, etc.). Failure to provide the same configuration may result to an invalid signature.

`AttestationPayloadParameters` interface is used to configure the claims. It's possible to define technical claims (i.e. issuance date, expiration date, etc.) or claims that can be selectively or non selectively disclosable. Helper methods are present for known claims, but it is also possible to define your own claim structures, using the specific implementation of `AttestationClaim`, `AttestationClaimArray` and `AttestationClaimObject`. The exact implementations of the class depend on the selected attestation format.

NOTE: It is up to the implementers to ensure validity of the attestation payload to a certain attestation profile.

[[AttestationSDService]]
==== AttestationSDService

`AttestationSDService` represents an extension of the `AttestationService` providing additional functionality on managing selectively disclosable claims, as well as attestation issuance.

A selectively disclosable credential allows the holder to reveal only the claims required for a particular transaction, as the opposite to a traditional credential revealing all contained information.

The service is also intended to be used by an attestation issuer.

The following methods are provided within the service:

* `#generateDisclosures(AttestationPayloadParameters)` - generates disclosures for every claim marked as selectively disclosable in the supplied payload parameters.
* `#issueAttestation(DSSDocument)` - creates an attestation to be transferred to a device containing only the signed attestation without
any selective disclosures.
* `#issueAttestation(DSSDocument, AttestationPayloadParameters)` - creates an attestation to be transferred to a device and automatically attaches all disclosures generated from the supplied payload parameters.
* `#issueAttestation(DSSDocument, List<SelectiveDisclosure>)` - creates an an attestation to be transferred to a device containing the supplied disclosures.

The selective disclosures are represented by the `SelectiveDisclosure` interface.

Below is a typical workflow of an attestation issuer using the `AttestationSDService` service.

[source]
.AttestationSDService workflow
----
ToBeSigned = getDataToSign(AttestationPayloadParameters, SerializableSignatureParameters)
        │
        ▼
SignatureValue = (external signing of ToBeSigned)
        │
        ▼
DSSDocument signedAttestation = signAttestation(AttestationPayloadParameters, SerializableSignatureParameters, SignatureValue)
        │
        ▼
List<SelectiveDisclosure> = generateDisclosures(AttestationPayloadParameters)
        │
        ▼
DSSDocument attestation = issueAttestation(DSSDocument signedAttestation, List<SelectiveDisclosure>)
----

==== AttestationPresentationService

`AttestationPresentationService` provides methods for processing an obtained attestation, device key binding signature creation as well as creation of attestation presentation.

An attestation presentation is a document created based on the existing attestation, a holder (e.g. a wallet) creates in order to provide a selected set of information to a relying party about the subject. An attestation presentation usually contains a list of disclosed claims as well as a key binding signature, a holder creates to confirm a valid possession of the attestation.

Below is an example of a created attestation presentation based on the issued attestation.

[cols="1,1"]
.Attestation Presentation creation
|===
|Issued attestation |Attestation presentation

|Attestation signature (payload)

+

Disclosures (Given name, Family name, Nationality, Date of Birth)

|Attestation signature (payload)

+

Disclosures (Given name, Family name)

+

Key binding signature
|===

The service is intended to be used by a device holder or a wallet.

The following methods are provided within the service:

* `#parseAttestation(DSSDocument)` - parses an issued attestation into its logical components.
* `#getDataToSignForKeyBindingSignature(DSSDocument, KeyBindingParameters, SerializableSignatureParameters)` - creates the format-specific data to be signed by a device key for a key-binding signature.
* `#getDataToSignForKeyBindingSignature(DSSDocument, List<SelectiveDisclosure>, KeyBindingParameters, SerializableSignatureParameters)` - creates the format-specific data to be signed by a device key for a key-binding signature covering the supplied disclosures.
* `#createKeyBindingSignature(DSSDocument, KeyBindingParameters, SerializableSignatureParameters, SignatureValue)` - produces a key-binding signature document from the supplied signature value. The signature value must sign the DTBS previously obtained through `#getDataToSignForKeyBindingSignature` method.
* `#createKeyBindingSignature(DSSDocument, List<SelectiveDisclosure>, KeyBindingParameters, SerializableSignatureParameters, SignatureValue)` - produces a key-binding signature document from the supplied signature value and disclosures. The signature value must sign the DTBS previously obtained through `#getDataToSignForKeyBindingSignature` method.
* `#issuePresentation(DSSDocument, List<SelectiveDisclosure>)` - creates an attestation presentation containing the signed attestation and
the supplied disclosures.
* `#issuePresentation(DSSDocument, DSSDocument)` - creates an attestation presentation containing the signed attestation and a holder key-binding signature.
* `#issuePresentation(DSSDocument, List<SelectiveDisclosure>, DSSDocument)` - creates an attestation presentation containing the signed attestation, the selected disclosures, and a holder key-binding signature.

`KeyBindingParameters` contain configuration for the key binding signature creation, such as key binding signature claims.

Please note that the service allows parsing of the original attestation, thus allowing to process and select selectively disclosable claims to be supplied with the attestation presentation.

Below is a typical workflow of a wallet using the `AttestationPresentationService` service.

[source]
.AttestationSDService workflow
----
DSSDocument attestation = (obtain attestation)
        │
        ▼
AttestationDocument = parseAttestation(DSSDocument attestation)
        │
        ▼
DSSDocument signedAttestation = AttestationDocument#getSignedAttestation
        │
        ▼
List<SelectiveDisclosure> = (select selectively disclosable claims to be presented from AttestationDocument)
        │
        ▼
ToBeSigned = getDataToSignForKeyBindingSignature(DSSDocument signedAttestation, List<SelectiveDisclosure>, KeyBindingParameters, SerializableSignatureParameters)
        │
        ▼
SignatureValue = (external signing of ToBeSigned)
        │
        ▼
DSSDocument keyBindingSignature = createKeyBindingSignature(DSSDocument signedAttestation, List<SelectiveDisclosure>, KeyBindingParameters, SerializableSignatureParameters, SignatureValue)
        │
        ▼
DSSDocument attestationPresentation = issuePresentation(DSSDocument signedAttestation, List<SelectiveDisclosure>, DSSDocument keyBindingSignature)
----

====== Salt

Each selectively disclosable claim is committed to in the attestation payload as the hash of a **disclosure** structure. For SD-JWT, a disclosure is the base64url-encoded JSON array `[salt, claim_name, claim_value]`, and its hash is placed in the `_sd` array. The salt is a cryptographically random value (at least 128 bits) that prevents an attacker from guessing a claim value by precomputing hashes of known inputs.

**Default salt generation**

DSS automatically generates a 128-bit salt for every selectively disclosable claim during payload building. Internally, the `SDJWTPayloadBuilder` seeds a `SecureRandom` deterministically from a hash of `payloadParameters.toString()` (via `DSSSecureRandomProvider`). This means that the same payload parameters configuration will always produce the same salts.

**Custom salt per claim**

When creating custom selectively disclosable claims, an explicit base64url-encoded salt can be supplied directly on the claim object:

====== Salt

Each `IssuerSignedItem` in an mdoc credential contains a random salt (raw byte array, at least 128 bits). This salt is CBOR-encoded together with the element identifier and value before the digest is computed, preventing an attacker from guessing a claim value by precomputing digests of known inputs.

**Default salt generation**

DSS automatically generates a 128-bit salt for every selectively disclosable claim during payload building. The same deterministic `DSSSecureRandomProvider` used for SD-JWT is applied here: the `SecureRandom` is seeded from a hash of `payloadParameters.toString()`, so the same payload parameters configuration will always produce the same salts.

**Custom salt per claim**

===== Key Binding

The implementation of signature parameters to use for the key binding (DeviceAuthentication) signature is `CBAdESSignatureParameters` with the following requirements :

=== Validation

==== Attestation document validation

The attestation validation follows the same pattern as regular signature validation. The entry point is `DefaultAttestationDocumentValidator`, which extends `SignedDocumentValidator`.

The validator can be obtained in two ways:

1. **Automatic format detection** via `DefaultAttestationDocumentValidator.fromDocument(dssDocument)` – the appropriate implementation is resolved using a `ServiceLoader` (requires the specific format module on the classpath).

2. **Direct instantiation** of a format-specific validator:
* SD-JWT:
** `SDJWTCompactDocumentValidator`: SD-JWT in compact serialization (`header.payload.signature\~disclosures~kbjwt`).
** `SDJWTJsonSerializationDocumentValidator`: SD-JWT in JSON serialization.

* ISO/IEC-mdoc:
** `MdocDeviceResponseDocumentValidator`: mdoc DeviceResponse (full presentation with device authentication). It performs the validation of an attestation presentation, applying the logic as defined in TS 119 472-2, section 4.2 EAAP implementation based on ISO/IEC-mdoc (<<R36>>)
** `MdocIssuerSignedDocumentValidator`: mdoc IssuerSigned only (without device authentication). It performs the validation of an attestation presentation as defined in TS 119 472-1, section 6 Implementation of attestation based on ISO/IEC-mdoc (<<R34>>)

The validator:

* verifies the issuer signature;
* extracts and validates selectively disclosed claims (when present);
* verifies the holder key-binding signature (when present);
* validates revocation status;
* validates qualification level (e.g. (Q)EAA, PuB-EAA, PID, etc.).

==== Revocation

DSS supports revocation checking for attestation presentations. Revocation information is provided to the validator via an `AttestationRevocationSource` instance set on the validator before calling `validateDocument()`.

Two base revocation mechanisms are defined:

* **Token Status List** – as per IETF `draft-ietf-oauth-status-list` (cf. <<R44>>) (JWT or CWT encoded).
** JWT Status List: implemented in `dss-attestation-revocation-jwt`.
** CWT Status List: implemented in `dss-attestation-revocation-cwt`.
* **Identifier List** – as per ISO/IEC 18013-5 (CWT encoded).
** Implemented in `dss-attestation-revocation-cwt`.

The ETSI TS 119 472-1 v1.2.1 (<<R34>>) variant of the Token Status List is also supported and is handled automatically by the `ETSI194721V121TokenStatusListValidator`.

The actual `AttestationRevocationValidator` to use is automatically selected at runtime via a `ServiceLoader` based on the revocation information embedded in the attestation payload. It is therefore necessary to include the appropriate revocation module on the classpath and register the corresponding `AttestationRevocationValidator` implementation in `META-INF/services`.

==== Inspection of Validation Reports

After calling `validateDocument()`, the three standard DSS reports are available: `DiagnosticData`, `SimpleReport`, and `DetailedReport`. The `DiagnosticData` exposes attestation specific information through `AttestationWrapper` objects.

For obtaining information about an attestation qualification, please see <<AttestationQualification>>.
