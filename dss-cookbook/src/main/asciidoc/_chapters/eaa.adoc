== Electronic Attestations of Attributes (EAA)

Electronic Attestations of Attributes (EAA) are digital identity credentials defined within the European Digital Identity (EUDI) framework. They allow the selective disclosure of identity attributes (claims) to a verifier, without exposing the full content of the credential. DSS provides support for issuing, presenting and validating EAA in two standard formats:

* **SD-JWT VC** (Selective Disclosure JWT Verifiable Credential) (<<R36, [R36]>>)
* **ISO/IEC 18013-5 mdoc** (Mobile Document) (<<R38, [R38]>>)

=== Creation

The exact classes to use depends on the format of the EAA, but for each format there's an implementation of the following interface :

- `AttestationService` is the service that manages the workflow to create the EAA. It is used to compute the data to be signed, create the signed EAA, create the key binding signature and issue an EAA presentation.

This service relies on the following interfaces :

- `AttestationPayloadParameters` to configure the claims. It's possible to define technical claims (i.e. issuance date, expiration date, etc.) or claims that can be selectively or non selectively disclosable. Helper methods are present for known claims, but it is also possible to define your own claim structures, using the specific implementation of `AttestationClaim`, `AttestationClaimArray` and `AttestationClaimObject`.
- `KeyBindingParameters` for the parameters required for the keybinding signature.
- `SelectiveDisclosure` for the representation of the disclosure of the EAA.

==== SD-JWT VC
The implementation of `AttestationService` to use for SD-JWT VC EAA creation is `SDJWTService`.

This service relies on the following implementations :

* `SDJWTPayloadParameters` as the implementation of `AttestationPayloadParameters`, with the following classes to define your own claim structures:
** `SDJWTClaim` for simple key/value claims, array elements and selectively disclosable object keys
** `SDJWTClaimArray` for array-typed claims
** `SDJWTClaimObject` for object-typed claims
* `SDJWTKeyBindingParameters` as the implementation of `KeyBindingParameters`.
* `SDJWTSelectiveDisclosure` as the implementation of `SelectiveDisclosure`.

===== Payload creation
`SDJWTPayloadParameters` allows defining claims for the EAA. It contains helper methods for known claim types. These known claims can be:

* Technical claims (`iss`, `iat`, etc.). Technical claims are always non-selectively disclosable in the produced EAA.
* Selectively disclosable claims.
* Non-selectively disclosable claims.

Custom claim structures can be built using `SDJWTClaim`, `SDJWTClaimArray` and `SDJWTClaimObject`, allowing selective disclosure at the individual element or property level.

====== Salt

Each selectively disclosable claim is committed to in the EAA payload as the hash of a **disclosure** structure. For SD-JWT VC, a disclosure is the base64url-encoded JSON array `[salt, claim_name, claim_value]`, and its hash is placed in the `_sd` array. The salt is a cryptographically random value (at least 128 bits) that prevents an attacker from guessing a claim value by precomputing hashes of known inputs.

**Default salt generation**

DSS automatically generates a 128-bit salt for every selectively disclosable claim during payload building. Internally, the `SDJWTPayloadBuilder` seeds a `SecureRandom` deterministically from a hash of `payloadParameters.toString()` (via `DSSSecureRandomProvider`). This means that the same payload parameters configuration will always produce the same salts.

**Custom salt per claim**

When creating custom selectively disclosable claims, an explicit base64url-encoded salt can be supplied directly on the claim object:

===== Signed EAA creation

The implementation of signature parameters to use for this format is `JAdESSignatureParameters` with the following requirements :

- The signature level must be `JAdES_BASELINE_B`.
- The signature packaging must be `ENVELOPING`.

If these parameters are not defined, these values will be set automatically.

NOTE: The `JWSSerializationType` can be set to `COMPACT_SERIALIZATION` (default SD-JWT VC format) or `JSON_SERIALIZATION` / `FLATTENED_JSON_SERIALIZATION`.

WARNING: The payload and signature parameters that are provided to get the data to be signed and to create the signed EAA must be equivalent. A mismatch may result in an invalid signature.

===== Key Binding

The implementation of signature parameters to use for the key binding signature of SD-JWT VC EAA is `JAdESSignatureParameters` with the following requirements :

- The signature level must be `JAdES_BASELINE_B`.
- The signature packaging must be `ENVELOPING`.
- The JWT serialization type must be `COMPACT_SERIALIZATION`.

If these parameters are not defined, these values will be set automatically.

The requirements for `SDJWTKeyBindingParameters` are that at least the nonce and the audience must be provided.

NOTE: If no issuance time is provided, the signing date from the key binding signature parameters will be used.

WARNING: The key binding parameters and signature parameters that are provided to get the data to be signed and to create the key binding signature must be equivalent. A mismatch may result in an invalid key binding signature.

==== ISO/IEC 18013-5 mdoc
The implementation of `AttestationService` to use for ISO/IEC 18013-5 mdoc EAA creation is `MdocService`.

This service relies on the following implementations :

* `MdocPayloadParameters` as the implementation of `AttestationPayloadParameters`, with the following class to define custom claim structures:
** `MdocClaim` for arbitrary selectively disclosable elements defined by a namespace, an element identifier and a value
* `MdocKeyBindingParameters` as the implementation of `KeyBindingParameters`.
* `MdocSelectiveDisclosure` as the implementation of `SelectiveDisclosure`.

===== Payload creation
`MdocPayloadParameters` allows defining claims for the EAA. It contains helper methods for known claim types (given name, family name, issuing country, etc.). All claims are selectively disclosable and are automatically assigned to the matching ISO/IEC namespace based on the configured `docType`. Technical claims (`validFrom`, `validUntil`, `docType`, `version`, `deviceKey`) are always part of the MSO and are not selectively disclosable.

====== Salt

Each `IssuerSignedItem` in an mdoc credential contains a random salt (raw byte array, at least 128 bits). This salt is CBOR-encoded together with the element identifier and value before the digest is computed, preventing an attacker from guessing a claim value by precomputing digests of known inputs.

**Default salt generation**

DSS automatically generates a 128-bit salt for every selectively disclosable claim during payload building. The same deterministic `DSSSecureRandomProvider` used for SD-JWT VC is applied here: the `SecureRandom` is seeded from a hash of `payloadParameters.toString()`, so the same payload parameters configuration will always produce the same salts.

**Custom salt per claim**

When creating custom claims using `MdocClaim`, an explicit salt (byte array) can be supplied directly on the claim object:

NOTE: For known claims (those set via helper methods such as `setGivenName()`, `setFamilyName()`, etc.), the salt is always generated automatically and cannot be overridden through the claim API.

===== Signed EAA creation

The implementation of signature parameters to use for this format is `CBAdESSignatureParameters` with the following requirements :

- The signature level must be `CB_AdES_BASELINE_B`.
- The signature packaging must be `ENVELOPING`.
- The COSE structure type must be `COSE_SIGN1` (untagged).
- Only ECDSA or EdDSA encryption algorithms are supported.
- The certificate chain must be included (`setIncludeCertificateChain(true)`).

If these parameters are not defined, these values will be set automatically.

NOTE: If no `docType` is defined, `MdocService` will attempt to derive it automatically from the list of configured claims (e.g. driving-privilege claims → `org.iso.18013.5.1.mDL`, EUDI PID claims → EUDI PID docType, ISO 23220-1 claims → `org.iso.23220.1.mID`).

WARNING: The payload and signature parameters that are provided to get the data to be signed and to create the signed EAA must be equivalent. A mismatch may result in an invalid signature.

===== Key Binding

The implementation of signature parameters to use for the key binding (DeviceAuthentication) signature is `CBAdESSignatureParameters` with the following requirements :

- The signature level must be `CB_AdES_BASELINE_B`.
- The signature packaging must be `DETACHED`.
- Only ECDSA or EdDSA encryption algorithms are supported.
- The certificate chain must not be included.

The key binding signature requires a `SessionTranscript` structure encoding the reader engagement (e.g., NFC Handover, QR code). This is built using the `SessionTranscriptBuilder`.

NOTE: If no session transcript is provided, `MdocKeyBindingParameters` will still produce a valid DeviceAuthentication structure, but without the reader-engagement binding.

WARNING: The key binding parameters and signature parameters that are provided to get the data to be signed and to create the key binding signature must be equivalent. A mismatch may result in an invalid key binding signature.

=== Validation

==== EAA presentation validation

The EAA presentation validation follows the same pattern as regular signature validation. The entry point is `DefaultAttestationDocumentValidator`, which extends `SignedDocumentValidator`.

The validator can be obtained in two ways:

1. **Automatic format detection** via `DefaultEAAPresentationValidator.fromDocument(dssDocument)` – the appropriate implementation is resolved using a `ServiceLoader` (requires the specific format module on the classpath).

2. **Direct instantiation** of a format-specific validator:
* SD-JWT: It performs the validation of an EAA presentation as defined in TS 119 472-2, section 4.1 EAAP implementation based on SD-JWT VC (<<R36,[R36]>>)
** `SDJWTCompactAttestationDocumentValidator`: SD-JWT VC in compact serialization (`header.payload.signature\~disclosures~kbjwt`).
** `SDJWTJsonSerializationAttestationDocumentValidator`: SD-JWT VC in JSON serialization.

* ISO/IEC-mdoc
** `MdocDeviceResponseAttestationDocumentValidator`: mdoc DeviceResponse (full presentation with device authentication). It performs the validation of an EAA presentation as defined in TS 119 472-2, section 4.2 EAAP implementation based on ISO/IEC-mdoc (<<R36,[R36]>>)
** `MdocIssuerSignedAttestationDocumentValidator`: mdoc IssuerSigned only (without device authentication). It performs the validation of an EAA presentation as defined in TS 119 472-1, section 6 Implementation of EAA based on ISO/IEC-mdoc (<<R34,[R34]>>)

==== Revocation

DSS supports revocation checking for EAA presentations. Revocation information is provided to the validator via an `AttestationRevocationSource` instance set on the validator before calling `validateDocument()`.

Two base revocation mechanisms are defined:

* **Token Status List** – as per IETF `draft-ietf-oauth-status-list` (JWT or CWT encoded).
** JWT Status List: implemented in `dss-attestation-revocation-jwt`.
** CWT Status List: implemented in `dss-attestation-revocation-cwt`.
* **Identifier List** – as per ISO/IEC 18013-5 (CWT encoded).
** Implemented in `dss-attestation-revocation-cwt`.

The ETSI TS 119 472-1 v1.2.1 (<<R34,[R34]>>) variant of the Token Status List is also supported and is handled automatically by the `ETSI194721V121AttestationStatusListValidator`.

The actual `AttestationRevocationValidator` to use is automatically selected at runtime via a `ServiceLoader` based on the revocation information embedded in the EAA payload. It is therefore necessary to include the appropriate revocation module on the classpath and register the corresponding `AttestationRevocationValidator` implementation in `META-INF/services`.
